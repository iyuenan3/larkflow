# PRD · larkflow（飞流）

## 目标
团队（先 Maxwell + 其团队）在飞书里「一句话发起 → AI 编排 → 派活给人 + AI 干 → 评分门禁 → 追踪收口」跑通完整闭环，前端只用飞书原语。

## 用户问题
组长 / 团队在飞书上反复手工派活、追进度、催办、汇总收口：无编排、无依赖解锁、无质量门、无可追踪的实例状态。协调劳动重且不留痕。

## 首个场景与成功指标（win：先证采用 + 门禁）
- **首个工作流** = 缺陷生命周期（见 ARCHITECTURE / DECISIONS ADR-009）。
- **第一个 win（可判定）**：一个真实 bug 从上报走到收口，中途 **G5 验证门禁 reopen 打回过一次没修好的提交**，团队成员**真的通过 larkflow 派的飞书任务处理了它**，最后自动收口 + 通知上报人。
- 这一条同时证「团队真穿过它（采用）」和「门禁真拦住（质量门价值）」。**省 leader 力是副产品**，不单列。
- 后续量化：从「一句话 / 事件触发」到「派单卡发出」时延；人工协调工时下降。

## UX 哲学
- **cards-only**（MVP，ADR-011）：app 注册到工作台 + bot + 交互卡片 + 飞书任务，近乎零前端；小程序 / H5 全局面板延后。
- 一句话触发；AI 干活，人把关（评分门禁 + human 审核节点）。
- 单一事实源在引擎，人看到的是投影，永远一致。

## 关键假设（赌注）
- 团队高频流程能被少量策展模板覆盖 + few-shot 生成扩展（ADR-003 / ADR-010）。
- 飞书原语（任务 / 卡片 / 多维表格）足以承载 UI，无需自建前端。

## 风险（pre-mortem，一行）
- 最大风险 = 采用：团队绕过 larkflow 继续老方式（靠选高频真痛的缺陷流 + 卡片体感不输手工缓解）。
- 门禁不被认可：AI 评分 / 人审门被当添堵（靠第一段就让门禁真打回一次、体现价值）。
- 飞书事件入口（lark-cli event consume）断线 / 权限受限（已验机制可行，dev app 建好后验确切 EventKey）。
