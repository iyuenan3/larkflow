# PRD · larkflow（飞流）

## 目标
项目发起人在飞书里「发起项目（说人话 @bot 或选模板）→ AI 生成 / 选定流程图 → AI / 人（含子项目下钻）接力产出一份交付物 → 反复打回、选择性重算 → 认可后交付」跑通完整闭环，且流程图和交付物都能在项目进行中演化，前端 = 妙搭应用（那张活图画布是门面）+ 飞书原语。

## 用户问题
需要多方（多人 + AI）接力产出一份重要文档（合同 / PRD 等）的发起人：手动分工、催定稿、追版本、打回后全流程重来、AI 与人的产出对不上。协调劳动重且不留痕。

## 首个场景与成功指标（win：证交付物真流转 + 打回省算）
- **首个真实场景** = 一个「各自产出再合并」形态的交付物流转项目（独立 doc 拓扑，合同类最贴，ADR-018）。
- **seg-1 已验证载体** = 缺陷生命周期（8 节点，退化特例：交付物 = 修复、图固定单链），已本地跑通 interrupt/resume + 打回 + checkpointer（见 ARCHITECTURE / ADR-009 / ADR-012）。
- **第一个 win（可判定）**：一个真项目全程跑通，产出被发起人认可的交付物；中途至少一次**打回触发可感知省算**（被打回支的负责人未被重新派单、旧 handle 直接复用，省下 ≥1 次 AI 长文起草）；至少一次**运行中改图**（加节点 / 加审核）被引擎正确接住（v1.0 经轻量命令 / 卡片触发 `edit_graph`，可视化画布编辑 v2）；发起人可对某审核节点开 **auto-approve** 自动放行。
- **win 证引擎可行性、不证采用**：采用另设闸（非 Maxwell 参与人真手完成一环 + 自发起第 2 个真项目），见 ROADMAP〈采用 gate〉。
- 后续量化：从发起到派单时延；打回重算节省的重复工时；人工协调工时下降。

## UX 哲学
- **妙搭前端 + 飞书原语**（ADR-019 修订 ADR-011 的 cards-only）：核心是一个妙搭应用（项目列表 / 项目详情含活图画布 / 审核 / 待办）挂工作台，叠在飞书卡片 + 任务 + 交付物文档之上；前端是总览 + 操控层，卡片 / 任务 / 文档仍是引擎的手。
- AI 干活、人把关（approval_policy：单人 / 会签 / 投票阈值 / auto bypass，ADR-015 / ADR-025）。
- **入口**：@bot 说人话发起（意图路由 + 确认步：AI 提议项目定义、人确认 / 改）或结构化「新建项目」表单，都收敛到起实例（ADR-021）。
- **主要靠 AI 现场生成流程**：从人话生成业务图（种子 few-shot / 纯生成），过护栏 + 确认 + 活图人工补正，越用越准（飞轮，ADR-022）。
- **两视角**：参与人 chat-first（收卡 / 审 / 开文档），可进 app 看只读全貌画布；发起人 / 管理者可全域打回 + 改图（v1.0 走轻量命令 / 卡片，app 驾驶舱可视化编辑画布 = v2）（可见 ≠ 可操作，ADR-023）。
- 交付物是飞书文档：人可看 / 协同 / 评论审，机器可 fetch 正文；版本靠飞书原生。
- 单一事实源在引擎，人看到的是投影，永远一致；只改未来不改历史。

## 关键假设（赌注）
- 交付物统一成飞书文档 handle 可行（produce / consume / overwrite / 版本闭环已在测试组织实测通过，见 MEMORY / ADR-016）。
- 非技术用户能接受「图」这个心智（图的复杂度不能外泄到界面，待验 UX）。
- **AI 现场生成业务图的准确率可用**（护栏拒畸形 + 确认 + 活图补正 + 飞轮兜底；生成升为主路径，ADR-022）。
- 子项目下钻（节点展开成子流程）能自然表达多方接力、且不失控（深度上限，ADR-024）。
- **团队真高频复发这种活**（「≥2 个真人接力产一份文档 + 有 gate / 打回」）：整个产品最承重的假设，同时决定采用 / 生成飞轮燃料 / 选择性重算的并行旁支。**首场景选合同是按拓扑贴合、非按频次；频次待验**（过去 60-90 天此类协作的件数与卡点，见 ROADMAP 采用 gate）。若低频则换 beachhead（合同 → 团队高频的 PRD / 文档接力，ADR-012 已并列点名）。

## 风险（pre-mortem，一行）
- 最大风险 = 采用：发起人绕过 larkflow 继续老方式（靠选真痛的多方协作场景 + 打回省算的体感缓解）。
- 图心智外泄：把引擎复杂度暴露给非技术用户会劝退（靠妙搭前端做「受控」呈现，只给活图的业务视图、不露 LangGraph 内部，缓解）。
- 共享协同拓扑的 docx section 定位符（block_id）跨 update 稳定性未验（放 v2，先做独立 doc 拓扑）。
- 生成质量：AI 生成的流程图可能不对（独立开放轴；win 不押它、用策展图，兜底 = 确认步 + 受控活图人工补正，ADR-022）。

## 差异化 / 护城河（vs 飞书原生，待正面验证）
- 真对手不是「手工无工具」，是**飞书原生审批（加签 / 条件分支 / 转交）+ Base 自动化 + 云文档**，甚至同平台妙搭 automation / aily。风险里「绕过 larkflow」= 退回原生。
- 差异化假设（原生短期做不到、对首个合同流真痛的 2-3 条硬断言）：① **打回只惊动受影响的人 + 旁支自动复用旧 handle**（选择性重算；原生审批退回即全链重来）；② **同一 gate 人 / AI 可换执行体 + auto / 会签 / 打回流转**一体；③ **运行中受控改图**（原生流程发起后结构不可改）。
- **待验（写代码前近零成本）**：1 天用纯原生（审批 + Base + 云文档）手搓一个合同流 mock，对 win 逐格标「原生能 / 不能」，剩下的格子 = 护城河真实面积，据此把自研范围砍到最小、其余压回原生。
