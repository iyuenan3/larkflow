# PRD · larkflow（飞流）

## 目标
项目发起人在飞书里「发起项目 → AI / 人接力产出一份交付物 → 反复打回、选择性重算 → 认可后交付」跑通完整闭环，且流程图和交付物都能在项目进行中演化，前端 = 妙搭应用（那张活图画布是门面）+ 飞书原语。

## 用户问题
需要多方（多人 + AI）接力产出一份重要文档（合同 / PRD 等）的发起人：手动分工、催定稿、追版本、打回后全流程重来、AI 与人的产出对不上。协调劳动重且不留痕。

## 首个场景与成功指标（win：证交付物真流转 + 打回省算）
- **首个真实场景** = 一个「各自产出再合并」形态的交付物流转项目（独立 doc 拓扑，合同类最贴，ADR-018）。
- **seg-1 已验证载体** = 缺陷生命周期（8 节点，退化特例：交付物 = 修复、图固定单链），已本地跑通 interrupt/resume + 打回 + checkpointer（见 ARCHITECTURE / ADR-009 / ADR-012）。
- **第一个 win（可判定）**：一个真项目全程跑通，产出被发起人认可的交付物；中途至少一次**打回触发选择性重算、未受影响的旁支不重跑**；至少一次**运行中改图**（加节点 / 加审核）被引擎正确接住；发起人可对某审核节点开 **auto-approve** 自动放行。
- 后续量化：从发起到派单时延；打回重算节省的重复工时；人工协调工时下降。

## UX 哲学
- **妙搭前端 + 飞书原语**（ADR-019 修订 ADR-011 的 cards-only）：核心是一个妙搭应用（项目列表 / 项目详情含活图画布 / 审核 / 待办）挂工作台，叠在飞书卡片 + 任务 + 交付物文档之上；前端是总览 + 操控层，卡片 / 任务 / 文档仍是引擎的手。
- AI 干活、人把关（approval_policy：单人 / 会签 / auto bypass，ADR-015）。
- 交付物是飞书文档：人可看 / 协同 / 评论审，机器可 fetch 正文；版本靠飞书原生。
- 单一事实源在引擎，人看到的是投影，永远一致；只改未来不改历史。

## 关键假设（赌注）
- 交付物统一成飞书文档 handle 可行（produce / consume / overwrite / 版本闭环已在测试组织实测通过，见 MEMORY / ADR-016）。
- 非技术用户能接受「图」这个心智（图的复杂度不能外泄到界面，待验 UX）。
- 团队高频流程能被少量策展模板覆盖 + few-shot 生成扩展（ADR-003 / ADR-010）。

## 风险（pre-mortem，一行）
- 最大风险 = 采用：发起人绕过 larkflow 继续老方式（靠选真痛的多方协作场景 + 打回省算的体感缓解）。
- 图心智外泄：把引擎复杂度暴露给非技术用户会劝退（靠妙搭前端做「受控」呈现，只给活图的业务视图、不露 LangGraph 内部，缓解）。
- 共享协同拓扑的 docx section 定位符（block_id）跨 update 稳定性未验（放 v2，先做独立 doc 拓扑）。
