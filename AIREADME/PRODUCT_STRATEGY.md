# PRODUCT STRATEGY · larkflow

> 状态：Cloud-first Target + Bounded Internal Pilot · Scope-constrained · 2026-08-14

## 1. 当前决策依据

目前没有条件完成企业访谈、历史实例回溯和飞书原生对照实验。因此，项目不使用尚未采集的市场证据作为工程启动门，也不把这些假设写成已验证结论。

近期产品范围来自两层约束：

1. 既有 AIREADME 中已经形成的产品、责任和运行时边界。
2. 当前最小闭环只保留草稿、启动、节点执行、受控编辑、重启、进度和审计。

详细取舍见 [`research/design-simplification.md`](../research/design-simplification.md)。

## 2. 产品选择

larkflow 选择做飞书原生的企业协作与 Agent 工作流控制平面，不复制完整办公平台。近期目标是在云端完成一个单企业、单层 DAG 的最小闭环：

- 从启用模板或结构化定义创建实例草稿。
- 由人确认启动或丢弃草稿。
- 把每个节点绑定到唯一人类 Owner，并投影到飞书。
- 调度 Human、Agent 和 Tool 三类执行器。
- 支持进度、暂停、恢复、取消、受控编辑和重启。
- 保留版本、Attempt、审计和投影对账。
- 在授权范围内使用管理员发布的企业共享资料和当前项目上传件。
- 通过可替换 PlannerRuntime 与 AgentRuntime 隔离模型框架，不让运行时成为业务真相。

## 3. 用户与工作

- 项目 Owner 需要把一个已知流程变成可确认、可推进和可恢复的实例。
- 节点 Owner 需要知道自己负责什么、依赖什么、如何完成，以及自动执行失败后如何接管。
- 流程管理员需要维护少量模板，并保证运行中实例不被模板修改悄然改变。

当前不再预设 50 至 1000 人企业、每月 10 次、30% 降本等市场门槛。这些仍是未来研究问题，不是当前事实。

## 4. 核心价值

- 明确责任：每个节点始终能追溯到一个人。
- 明确启动：草稿不会因为生成或匹配成功而自动执行。
- 明确变化：编辑和重启都先展示影响范围，再由有权限的人确认。
- 明确恢复：业务状态保存在中央数据库，飞书对象丢失后可以重建。
- 明确边界：自动执行器帮助完成工作，不成为组织责任主体。
- 明确上下文：企业共享资料与项目上传分别授权，每次 Attempt 只拿到完成当前工作所需的最小上下文。

## 5. 本轮取舍

| 保留 | 简化 | 后置 |
|---|---|---|
| 模板可选、草稿确认、版本快照 | 项目工作区先由 Instance 元数据与项目上传件承载 | 独立 Project 聚合、子 DAG 与三级下钻 |
| Human、Agent、Tool 节点 | 五维评分改为可解释的 `pass/fail` | 个人 Agent Edge 的产品化、后台常驻与写能力 |
| 企业共享资料与项目级上传 | 只接受管理员发布的全企业共享语料，不复制源系统复杂 ACL | 个人知识库、部门知识库、通用企业搜索 |
| 未来区域编辑与二次确认 | 模板锁改为版本级布尔值 | 通用 RAG、能力注册表、模板市场 |
| 节点重启、下游重置、Attempt | 模块化单体加 PostgreSQL outbox | Kafka、微服务、复杂 ACL |
| 飞书投影、幂等、对账、审计 | Pi 与 DSH 只作为端口后实验适配器 | 自动企业 Process Map、Edge 产品化 |

## 6. 成功标准

当前阶段只使用功能与一致性标准：

1. 每项 MVP 能力都有明确的产品理由和可判定验收。
2. CORE、PRD、架构、模板契约、路线图、README 和包描述不再互相冲突。
3. Target 与 As-built 明确分开，不把 legacy 测试通过写成目标产品已实现。
4. 市场频率、收益和付费意愿继续标记为未知。
5. 开发真栈的接受、退回、重启和恢复路径不再通过更多合成点击重复证明，后续证据来自真实内部工作。

## 7. 未来验证

访谈与对照实验协议保留在 [`research/phase-0/`](../research/phase-0/README.md)，状态为 Deferred。具备条件后再验证首个场景、真实频率、增量价值和购买意愿，不用文档一致性代替市场证据。

Personal Agent Edge 已完成窄 Proof，但不是当前核心问题，自 2026-08-14 起暂停。恢复前必须证明存在云端无法满足的真实任务，并重新评估员工采用、组织数据政策、分发安全与管理成本。

Pi 与 DeepSeek Harness 的采用使用对照实验而不是架构偏好决定。候选适配器必须与当前 Python 基线使用相同输入、只读工具、校验器和输出合同，比较首次硬校验通过率、用户改图次数、遗漏输入、无效依赖、节点冗余、一次接受率、规划耗时与成本。若没有材料改善，或需要把数据库与飞书凭据交给运行时，就停止该适配器。

当前先执行受控内部试用，不把它包装成客户验证。优先使用 larkflow 项目自身真实存在的开发、复核和发布工作，记录实例完成、首次结果可用性、退回与返工、人工干预、明确决定耗时和重复外部副作用。首轮目标是建立可解释的小样本基线并发现产品摩擦，不预设收益百分比、规模容量或付费结论。
