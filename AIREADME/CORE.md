# CORE · larkflow（飞流）

## 身份

larkflow 是**基于飞书的企业协作 DAG 系统**。它把一个跨人、跨部门目标拆成可验收的工作包，把每个工作包分配给真实的人，并允许责任人在权限范围内继续展开子 DAG。飞书承载消息、待办、文档、云盘和组织身份；larkflow 负责模板、编排、责任边界、验收、返工和审计。

合同起草只是说明多部门协作的示例，不是产品定位或唯一首发场景。

## 使命

让企业已有的协作流程从“靠人记、靠群催、靠经验传”变成可复用、可委派、可追踪的组织能力。AI 的价值是帮助人完成工作，不是替代责任归属。

## 用户

- 发起人：提出跨团队目标，查看顶层进度并验收最终结果。
- 工作包责任人：接收飞书待办，选择亲自完成、调用个人 Agent，或创建下一级 DAG。
- 部门主管 / 流程 Owner：维护本部门模板、分派责任并处理跨边界阻塞。
- 企业管理员 / 流程管理员：完成企业入驻、资源授权、模板治理和审计。

## 产品不变量

1. **待办分配给人，不分配给 Agent。** 个人电脑离线不影响待办、责任和工作流状态。
2. **最多三级 DAG。** L1 企业/跨部门，L2 部门，L3 团队/个人；L3 不得继续下钻。
3. **父子 DAG 按工作契约连接。** 父层默认只看目标、状态、阻塞、交付物和验收记录，不穿透操控子层内部。
4. **DAG 保持无环。** 打回、重试和返工通过新的 Attempt 或重开状态表达，不画回边。
5. **模板版本不可变。** 实例固定到发布版本和完整快照，升级必须显式 diff/merge。
6. **中央控制面是业务真相源。** 飞书是用户入口和工作投影；LangGraph 只能作为 AI 节点内部的可选运行时。
7. **权限由服务端计算。** 不信任卡片、客户端或本地 Agent 提交的身份与图修改权限。

## Non-goals

- 不替代飞书，不自研 IM、云盘、云文档、通讯录或通用任务系统。
- 不做“Agent 帮个人建几个待办”的单机效率工具。
- 不承诺入驻时一次性学习企业全部知识；采用授权、渐进发现、人工确认。
- 不把 LangGraph、prompt 或 MCP 细节暴露为业务模板心智。
- MVP 不做无限层级、任意循环、全自动组织改造或无人工治理的模板发布。

## 当前阶段

仓库已有一个 LangGraph + SQLite + lark-cli 的中心化流程原型，验证了飞书卡片、任务、文档投影、打回和恢复等机制。它不是目标产品架构。后续实现必须以本文件、PRD、DAG Template Spec 和新 ADR 为准，并把可复用机制逐步迁入多租户中央控制面。
