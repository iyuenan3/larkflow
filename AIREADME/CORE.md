# CORE · larkflow（飞流）

## 身份
飞书原生的**交付物流转**工作流引擎。用户发起一个项目（要产出一份交付物：合同 / PRD / 任何文档），larkflow 把它编排成一张**项目进行中可编辑的图**：AI / 人 / 工具节点接力生产与审核交付物，任意节点可打回、只重算受影响的部分，直到发起人认可后交付。全程落在飞书里。

## 使命
把「多方（多人 + 多 AI）接力产出一份交付物」的协调劳动，变成飞书里可视、可流转、可追溯的工作流：AI 节点扛收集 / 起草 / 整合的重活，人只在关键处把关（可 bypass 自动放行），交付物反复打回重写不丢版本，流程图中途还能改。

## 用户
项目发起人（产品经理 / 法务 / 业务负责人等，需要多方接力产出一份重要文档的人）。先 Maxwell 自己 + 其带的团队（dogfood）。形态 = 飞书企业自建应用，挂工作台。开发在独立 dev 飞书租户（clean-room 测试组织，ADR-008）。

## Non-Goals（明确不做）
- 不做通用 iPaaS / Zapier 式集成平台（只做飞书原生的交付物流转编排）。
- MVP 前端 = 飞书卡片 + 飞书文档（cards-only，ADR-011）：app + bot + 交互卡片 + 任务 + 交付物文档，**不建小程序 / H5 面板**（延后）。
- 不做纯 DAG 无环编排（要打回 / 循环 / 选择性重算，用 LangGraph 的环）。
- 不做静态模板实例（图运行中不可改）：要「受控活图」，运行中可改未来节点（ADR-013）。
- 不对 C 端收费、不做独立 SaaS 门户（团队内部工具优先）。

## 绝不（硬约束红线）
- **单一事实源不破**：实例运行态由 LangGraph checkpointer 持有，是权威；飞书任务 / 文档 / 多维表格只是投影（交付物文档会被 overwrite，飞书 history 是投影侧 bonus），绝不反向当真相源写回。
- **只改未来、不改历史**：受控活图里已完成 / 在跑的节点冻结，只能增删改未来节点；打回是把执行前沿往回拉、解冻那段重跑（append 新版本），绝不原地改写已完成节点的历史产出（ADR-013 / ADR-014）。
- **完成靠显式信号，引擎不猜**：human 节点的「定稿 / 通过 / 打回」必须来自人主动发的信号（发消息 / 完成任务 / 点卡片），引擎绝不因「文档不动了」判定稿。
- **key / 凭证不入库**：飞书 app secret、LLM key、lark-cli token 走 env / keychain，绝不落 git、绝不进任何 AIREADME 文件。
- **LLM 走 OpenAI 兼容接口**（火山方舟 / 中转站 / 直连，按任务角色路由、各角色独立 key），不直连厂商专有 SDK（ADR-017）。
- **clean-room**：只借公开的架构范式，不复制任何雇主代码 / 业务数据 / 内部命名。

## 生命周期
立项（2026-07-23）。第一段本地引擎已跑通（8 节点缺陷流，LangGraph + SQLite，2026-07-24）。第二轮设计定：定位升格为交付物流转引擎（ADR-012..018）。第一里程碑 = 一个真实交付物流转项目（独立 doc 拓扑，合同类）端到端跑通。
